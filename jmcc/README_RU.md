# jmcc

> [!NOTE]
> Английская версия доступна в [README.md](README.md).

Компилятор: превращает программу на `.jc` в JSON-модуль `JustMC`, который
загружается в редактор сервера.

Схему модуля компилятор не выдумывает — она лежит в
[`jmcdata`](../jmcdata/README.md), и оттуда же приходят имена действий, событий
и наборы их аргументов. Выполняет готовый модуль [мок](../jmcmock/README.md);
`jmcc` его не запускает и запускать не умеет.

Компилятор — это ещё и определение языка. Ключевых слов в нём меньше, чем
кажется: операторы, литералы и большая часть «встроенных» действий написаны на
самом `.jc` и лежат в `std/`. Какие именно — в разделе
[`std/` — это и есть язык](#std--это-и-есть-язык).

## Запуск

Две подкоманды: `compile` и `format`.

```bash
RUST_LOG=warn cargo run -p jmcc -- compile jmcc/tests/case1.jc
RUST_LOG=warn cargo run -p jmcc -- format jmcc/tests/case2.jc
```

`RUST_LOG` не украшение: фильтр по умолчанию — `trace,egg=debug`, и без него
компилятор печатает в стандартный вывод ошибок сотни строк трассировки. При
`RUST_LOG=info` видно, какие проходы оптимизации запустились и сколько шли, — это
основной способ понять, что происходит.

### `jmcc compile`

| Ключ | Значение |
|---|---|
| `<input>` | файл `.jc`; от его каталога разрешаются импорты и пишутся дампы |
| `-o, --output <PATH>` | куда писать JSON; по умолчанию рядом с входным файлом, с тем же именем |
| `-O, --opt-level <0..3>` | уровень оптимизаций, по умолчанию `2` |
| `--passes <A,B>` | включить проходы по имени, через запятую |
| `--disable-passes <A,B>` | выключить проходы по имени |
| `--target <justmc>` | цель; пока единственная, и она же по умолчанию |
| `--edition <2023\|2026>` | издание языка, по умолчанию `2026` |
| `--emit <ast,hir,mir,json>` | что писать на диск; по умолчанию всё четыре |

`--emit` управляет только записью на диск. Если `json` не указан, кодогенерация
пропускается целиком — компилятор честно пишет в журнал
`JSON generation skipped`, и никакого модуля не появляется.

Код возврата — `SUCCESS` при успехе и `FAILURE` при любой ошибке: нечитаемый
файл, ошибка разбора, ошибка семантики, ошибка развёртки перегрузок.

### `jmcc format`

| Ключ | Значение |
|---|---|
| `<input>` | файл `.jc` или каталог; каталог обходится рекурсивно, берутся только `.jc` |
| `--check` | ничего не писать и вернуть `FAILURE`, если хоть один файл отличается |

Форматтер разбирает файл с жёстко заданными `edition = 2026` и `offset = 0` и
**не разрешает импорты**. Поэтому файл, который не собирается без соседей,
всё равно форматируется — и наоборот, ничто не мешает отформатировать файл,
который потом не скомпилируется.

### Чего компилятор не делает

Он ничего не печатает в стандартный вывод: всё, включая ошибки, идёт через
`tracing` в стандартный вывод ошибок. Это не случайность — `clippy::print_stdout`
в линтах воркспейса запрещён, и единственный вывод компилятора — файлы на диске.

## Что происходит при компиляции

Порядок шагов — это `run_compile` в [`main.rs`](src/main.rs), и он же
единственное место, где виден весь конвейер:

1. `ast::parse_file(path, edition)` ([`ast/import.rs`](src/ast/import.rs)) —
   лексер, парсер и разрешение импортов. Импортируемые файлы разбираются здесь
   же, рекурсивно.
2. `ast::analyze(&ast, &source, &ir_ctx, edition)`
   ([`ast/semantic.rs`](src/ast/semantic.rs)) — вывод типов, проверка имён,
   областей видимости и наборов аргументов. Именно здесь появляются
   человекочитаемые «at file.jc:12:5: …»: номер строки и колонки берутся из
   `Ast::line_indexes` — `line_index::LineIndex` на каждый файл из
   `Ast::sources`, построенный там же, где текст попадает в `Ast`.
3. `ir::hir::ast_to_hir(...)` ([`ir/hir.rs`](src/ir/hir.rs)) — понижение AST в
   HIR. Классы, типы и перегрузки здесь ещё видны.
4. `ir::opt::optimize(hir, …)` — оптимизации HIR.
5. `ir::hir_expand::expand_overloads(...)`
   ([`ir/hir_expand.rs`](src/ir/hir_expand.rs)) — то, что делает язык языком:
   `a + b` превращается в тело `__add__`, `if (a > b)` — в тело `__greater__`.
   После этого шага в HIR не остаётся ни одного оператора.
6. `ir::mir::lower_to_mir(&hir, &ir_ctx, edition)` ([`ir/mir.rs`](src/ir/mir.rs)) —
   понижение в MIR: теперь это почти действия, и каждое типизировано под схему.
7. `ir::opt::optimize(mir, …)` — оптимизации MIR.
8. `ir::codegen::CodeGen::generate(&mir)` ([`ir/codegen.rs`](src/ir/codegen.rs)) —
   сборка `jmcdata::module::Module`, `serde_json::to_string_pretty` и запись.

Шаги 4 и 7 — один и тот же `optimize`, вызванный дважды с разными наборами
проходов. Поэтому в журнале имя прохода встречается по нескольку раз, и это не
дублирование вывода.

## Дампы

Дампы — не отладочный вывод, а основной способ проверить изменение: тестов у
`jmcc` нет, и «проход сработал» доказывается только прочитанным дампом.

| Файл | Что внутри |
|---|---|
| `<stem>.ast` | дерево после разбора, до анализа |
| `<stem>_noopt.hir` | HIR до оптимизаций |
| `<stem>_opt_preoverloads.hir` | HIR после оптимизаций, до развёртки перегрузок |
| `<stem>.hir` | HIR после развёртки перегрузок — то, что понижается в MIR |
| `<stem>_noopt.mir` | MIR сразу после понижения |
| `<stem>.mir` | MIR после оптимизаций — то, что уходит в кодогенерацию |
| `<stem>.json` | модуль (или путь из `-o`) |

`.ast` пишется **до** семантического анализа, поэтому он остаётся на диске даже
у файла, который не скомпилировался. Это единственный дамп, у которого есть
такое свойство: остальные появляются по мере прохождения шагов.

Все три HIR и оба MIR пишутся через `RecExpr::pretty(80)` — это S-выражения с
отступом в 80 единиц, и в них видно ровно то, что лежит в дереве. Читать их
следует сверху вниз: корень — `(block ...)`, внутри — объявления обработчиков.

## HIR и MIR

Оба представления — `egg::define_language!`-перечисления
([`ir/hir.rs`](src/ir/hir.rs), [`ir/mir.rs`](src/ir/mir.rs)) и лежат в
`RecExpr<Hir>` / `RecExpr<Mir>`.

`egg` здесь используется **только как контейнер S-выражений**. Ни e-графов, ни
правил перезаписи, ни `Runner` в компиляторе нет и не должно быть: проходы —
это обычные функции `RecExpr -> RecExpr`, написанные руками. Максимум, что
берётся из `egg`, — `Id`, `RecExpr`, `Symbol` и `map_children`. Поэтому
предложения «сформулировать это правилом перезаписи» здесь неуместны, а
`define_language!` стоит читать как «объявление вариантов с автоматической
упаковкой детей в срез `Id`».

Разница между представлениями простая:

* **HIR** ближе к исходнику. В нём есть классы, параметры, типы-заглушки,
  `Named`-аргументы, а операторы ещё не развёрнуты. Имена локальных
  переменных — те, что написал программист.
* **MIR** ближе к JSON. Одно действие — один узел `Mir::Action`, ветвления
  разложены на `container`/`condition`/`else`, а имена переменных уже
  заменены на то, что поймёт `JustMC` (включая области видимости).

Между ними стоит развёртка перегрузок, и это самая неочевидная часть
конвейера:

```
AST                    HIR                     MIR                  JSON
a > b   ──analyze──▶  Gt(a, b)  ──expand──▶  Action(variable greater)  ──codegen──▶  op
```

## Оптимизации

`ir::opt::optimize` ([`ir/opt/mod.rs`](src/ir/opt/mod.rs)) принимает выражение,
наборы проходов и `OptConfig { opt_level, enabled_passes, disabled_passes }`.

### Как выбирается, что запускать

Имя прохода — это `Debug` варианта перечисления, обрезанный по первой `(` и
приведённый к нижнему регистру. Варианты держат внутри структуру, поэтому
`Debug` даёт `Inline(InlinePass { … })`, а именем становится `inline`. Отсюда
практическое следствие: в `--passes` пишется имя **варианта**, а не структуры,
и угадать его по исходнику нельзя — проще запустить компиляцию с
`RUST_LOG=info` и прочитать список.

Правило включения, по порядку:

1. если имя есть в `--disable-passes` — проход выключен, и это сильнее всего;
2. если имя есть в `--passes` — проход включён;
3. иначе — включён тогда, когда `--passes` пуст **и** `opt_level()` прохода не
   больше `-O`.

Третий пункт объясняет, почему `--passes inline` не «добавляет инлайн ко
всему остальному», а оставляет **только** инлайн: непустой `--passes` глушит
все проходы, которых в нём нет.

Проходы по модулю выполняются один раз. Проходы по функциям — до неподвижной
точки, но не больше трёх раундов: `run_function_pass` прогоняет проход по
каждому телу отдельно, пересобирая `RecExpr`.

Сам проход пишет только `const OPT_LEVEL: u8` и `run`; `opt_level()` — provided
метод трейта (`Self::OPT_LEVEL`). Четыре перечисления-диспетчера
(`{Hir,Mir}{Module,Function}Passes`) не написаны руками: их порождает
`dispatch_passes!` из списка «вариант → тип» в `ir/opt/mod.rs`, поэтому
добавление прохода — это одна строка в списке плюс регистрация в
`all_module_passes` / `all_function_passes`.

**Ранний выход при этом не срабатывает.** `run_function_pass` дописывает
оптимизированное тело функции в новый вектор узлов, но старую копию оттуда не
убирает — она остаётся в `RecExpr` недостижимой из корня. Вектор узлов растёт,
сравнение `result == prev` всегда ложно, и три раунда — это всегда три раунда.
В дампе этого не видно: `pretty` печатает только достижимое из корня, и
`--passes noop` даёт побайтово одинаковые `_noopt.hir` и `_opt_preoverloads.hir`
ценой трёх полных проходов. Единственный случай, когда видно строку
`Function passes converged after 0 rounds`, — стадия, в которой не включено ни
одного прохода: так бывает у MIR на `-O0`.

### Что зарегистрировано

| Стадия | Проход | Уровень | Что делает |
|---|---|---:|---|
| HIR, модуль | `testhirmodulepass` | 1 | ничего; печатает в журнал и возвращает выражение как есть |
| HIR, модуль | `inline` | 2 | инлайнит функции по стоимости; порог зависит от `-O` |
| HIR, модуль | `deadfunctionelimination` | 1 | выбрасывает функции, на которые никто не ссылается |
| HIR, функция | `noop` | 0 | ничего; существует, чтобы стадия не была пустой |
| HIR, функция | `constantfolding` | 1 | сворачивает константные выражения |
| HIR, функция | `algebraicsimplification` | 1 | тождества вида `x + 0`, `x * 1` |
| HIR, функция | `copypropagation` | 1 | подставляет известные копии переменных |
| HIR, функция | `deadcodeelimination` | 1 | выбрасывает недостижимый код |
| MIR, модуль | `noop` | 0 | ничего |
| MIR, функция | `redundantreturnelimination` | 1 | убирает `return` в конце обработчика |
| MIR, функция | `copycoalescing` | 2 | склеивает цепочки копирований |
| MIR, функция | `setvariablefolding` | 2 | складывает присваивания в одно действие |
| MIR, функция | `coordinatefolding` | 2 | складывает разбор координат |
| MIR, функция | `redundantelseelimination` | 2 | убирает `else` без ветки |

Из таблицы видно, что уровни `-O2` и `-O3` дают **один и тот же** набор
проходов: всё, что меньше трёх, включается уже на `-O2`. Разница между `-O2` и
`-O3` только в одном числе — пороге инлайнера
(`DEFAULT_THRESHOLD = 225` против `AGGRESSIVE_THRESHOLD = 250`,
[`inline/cost.rs`](src/ir/opt/hir/inliner/cost.rs)). У `-O1` из HIR-проходов
остаются только уровневые единицы, а инлайнер выключается совсем: его проход второго уровня, а порог при `-O1` — 100, то есть инлайнится почти ничего.

## Издания

`--edition` переключает диалект языка. Различий ровно три, и все заметные:

| | `2023` | `2026` (по умолчанию) |
|---|---|---|
| прелюдия | `std/prelude_2023.jc` | `std/prelude_2026.jc` |
| имена | без манглинга | с манглингом (`tests::generator::test`) |
| импорт | приносит всё | приносит только то, что помечено `export` |
| область видимости по умолчанию | `local` | `line` |
| параметры процесса | пишутся `set`-ами до вызова | уезжают в `map` с именем `args` |

Прелюдия выбирается в [`ast/import.rs`](src/ast/import.rs), а область
видимости — в `CodeGen::new` ([`ir/codegen.rs`](src/ir/codegen.rs)). Обе
прелюдии (`std/prelude_2026.jc` и `std/prelude_2023.jc`) подключают `primitives`
и `math/core.jc`.

Издание 2023 поддерживается: проект `tests/pvp/main.jc` компилируется командой
`jmcc compile jmcc/tests/pvp/main.jc --edition 2023 --emit json`.
Область по умолчанию `local` учитывается при разборе и построении HIR;
плейсхолдеры интерполяции используют фактическую область переменной.
Успешная компиляция не означает полного покрытия серверных действий в `jmcmock`.

`format` всегда разбирает по изданию 2026, независимо от ключа: у него ключа
`--edition` нет.

## `std/` — это и есть язык

Операторы в `.jc` не встроены в компилятор. `a > b` — это вызов метода
`__greater__`, и живёт он в
[`std/primitives/code/number.jc`](std/primitives/code/number.jc):

```jc
@lang_item
inline class number {
    inline function __greater__(first: number, second: number) -> boolean {
        return first.greater(second);
    }
}
```

Классы с атрибутом `@lang_item` — те, которые компилятор узнаёт как встроенные
типы; их двадцать, по одному на файл в `std/primitives/`. Метод `__*__` на
таком классе и есть оператор:

| Оператор | Метод | Оператор | Метод |
|---|---|---|---|
| `+` | `__add__` | `-=` | `__isubtract__` |
| `-` | `__subtract__` | `*=` | `__imultiply__` |
| `*` | `__multiply__` | `/=` | `__idivide__` |
| `/` | `__divide__` | `%=` | `__iremainder__` |
| `%` | `__remainder__` | `^=` | `__ipow__` |
| `^` | `__pow__` | `[]` (чтение) | `__subscript__` |
| `==` | `__equals__` | `[]` (запись) | `__subscript__` с тремя параметрами |
| `!=` | `__not_equals__` | `[a:b]` | `__slice__` |
| `>` | `__greater__` | `in` | `__contains__` (вызывается от правого операнда) |
| `<` | `__less__` | `.` (чтение) | `__get_attribute__` |
| `>=` | `__greater_or_equals__` | `.` (запись) | `__set_attribute__` |
| `<=` | `__less_or_equals__` | конструктор | `__init__` |

`+=` и родственные по умолчанию раскрываются в `a = a + b`, то есть в
`__add__`; собственный `__iadd__` переопределяет это поведение. Семантический
анализ проверяет наличие dunder-метода (`__i*__` / `__*__`) у целевого типа,
поэтому составные присваивания поддерживаются для `number`, `text`, `array` и
любых классов с перегруженными операторами.

Отсюда практическое правило: **чтобы изменить смысл оператора, правится `.jc`,
а не Rust.** Компилятор о `__greater__` ничего не знает — он знает только, что
`a > b` нужно заменить на вызов метода `__greater__` от левого операнда.

Сам `std/` — это тоже обычный код на `.jc`, и он компилируется как любой
другой. Рядом с примитивами лежат библиотеки, которыми можно пользоваться:
`std/math/core.jc` и `std/math/matrix.jc`, `std/ai/astar.jc` и `std/ai/nn.jc`,
`std/security/modchecker.jc`, эффекты в `std/effects/text/`. Прелюдия 2026
подключает `primitives` и `math/core.jc` — остальное импортируется вручную.

## Что попадает в JSON

Модуль — это список обработчиков (`handlers`). `CodeGen::generate`
([`ir/codegen.rs`](src/ir/codegen.rs)) делает с ними четыре вещи, и каждая
удивит, если о ней не знать:

**Обработчики сортируются** по ключу `(вид, длина тела)`, где вид — `Event` (0),
`Function` (1), `Process` (2). Внутри вида — по числу операций.

**`position` — это не строка исходника.** Каждому обработчику при создании
ставится `position: 1337`, а в конце `generate` все они перенумеровываются:
`line.position = pos as u16`. То есть в JSON уходит порядковый номер
обработчика после сортировки, `0..n-1`. Искать по нему место в файле `.jc`
бессмысленно.

**Тело каждого обработчика оборачивается в замер времени.** Безусловно, поверх
всего, что написал программист:

```
controller::measure_time[ t = %var_line(t)% ]{ …тело… }
player::message["<имя> running time: %var_line(t)%"]
```

Имя — `Debug` события (то есть `PlayerJoin`) или имя функции. Флаг
`trace_runtime` в `CodeGen` жёстко равен `false`, так что эта обёртка —
единственное, что видно в модуле от отладки: по ней в игре можно понять,
сколько шёл обработчик, но не что именно он делал.

**Сверху появляется синтетический `world_start`.** Всё, что на верхнем уровне
файла не является объявлением, уезжает в обработчик события `world_start`, и он
эмитится, только если в нём что-то есть.

Функции получают лишний аргумент `description` со значением
`"Function: <имя>"` в режиме разбора `Legacy` — это подпись в редакторе
`JustMC`, а не часть программы.

## Устройство кода

```
src/
├── main.rs          CLI и конвейер: единственное место, где виден весь порядок шагов
├── error.rs         JmccError: ошибки разбора
├── diagnostic/      Pretty Diagnostics: annotate-snippets, коды E0001..E0103, подсветка спанов
├── project/         система проектов и зависимостей (jmcc.toml, workspace, git/path deps)
├── utils.rs         resolve_action_arg_def — сопоставление аргумента схеме; SNBT
├── ast/
│   ├── lexer.rs     лексер на logos
│   ├── ast_pretty.rs печать AST
│   ├── parser/      парсер в AST: mod (Parser и `parse_string`), decls, stmts,
│   │                exprs (Пратт), types, text
│   ├── import/      разрешение импортов: mod (`parse_file`, ImportResolver),
│   │                resolve (обход файлов), merge (слияние AST), export
│   │                (фильтр по `export`), mangle (имена модулей)
│   ├── semantic/    вывод типов и человекочитаемые ошибки: mod (типы, `Type`,
│   │                `Symbol`, `Analyzer`, вход `analyze`), scopes, types, decls,
│   │                stmts, exprs, calls, actions (аргументы действий)
│   └── format/      форматтер: mod (буфер и `format`), decls, stmts, exprs, text
└── ir/
    ├── arena.rs          NodeArena<L> — плотное хранилище узлов RecExpr
    ├── builder.rs        HirEmitter: общие хелперы двух HIR-построителей
    ├── walk.rs           обход поддерева RecExpr без повторного захода
    ├── schema.rs         фасад над схемой JustMC из jmcdata
    ├── ctx.rs            IrCtx: таблицы имён, типов и символов
    ├── constructors.rs   сборка Item, Location, Particle и прочего NBT
    ├── hir/              HIR и ast_to_hir: mod (язык `Hir`, `HirBuilder`,
    │                     `ast_to_hir`), scopes, decls, stmts, exprs, props,
    │                     calls, actions, text
    ├── hir_expand/       развёртка перегрузок: mod (`OverloadExpander`,
    │                     `expand_overloads`), types, scopes, stmts, exprs,
    │                     calls, text
    ├── mir/              MIR и lower_to_mir: mod (язык `Mir`, `MirLowerer`),
    │                     stmts, exprs, calls, action, vars
    ├── codegen/          MIR → Module: mod (`CodeGen`, `generate`), handlers,
    │                     ops, values, selectors
    └── opt/              проходы оптимизации (hir/, mir/ и общий optimize)
```

Разделение крупных модулей сделано **по ответственности, а не по размеру**: в
`mod.rs` каждого каталога лежат определения типов, точка входа и общая
инфраструктура, а `impl`-блоки разложены по детям (`scopes` — имена и области,
`exprs` — выражения, `calls` — вызовы и т. д.). Внешние пути при этом не
менялись: `crate::ast::semantic::Analyzer`, `crate::ir::hir::ast_to_hir` и
остальное доступны ровно так же, как до разделения. Цена — примерно 760 строк
служебных `//!`-доков, `mod`/`use`, обёрток `impl` и `pub(super)`; самый
большой файл крейта теперь `ast/semantic/actions.rs` (767 строк вместо 3493).

Приём «взять `Id` из длины вектора, положить узел, вернуть `Id`» живёт в
крейте ровно в одном месте — `NodeArena::add`. Все, кто строит `RecExpr`
вперёд (`HirBuilder`, `OverloadExpander`, `MirLowerer` и каждый проход,
который копирует DAG с перенумерацией `Id`), держат `NodeArena`, а не
`Vec<L>`; исключение — проходы, которые **мутируют** уже готовые узлы на
месте (`redundant_return_elimination`), потому что мутирующего доступа по
`Id` арена намеренно не даёт.

Два обхода каталогов (сбор `.jc` при импорте каталога и `jmcc format <dir>`)
идут через `walkdir`, а строка/колонка диагностики — через
`line-index`/`text-size`. Подробности и проверки — в
`docs/superpowers/specs/2026-09-16-jmcc-dedup-design.md`, §4.9 и §9.

Полезно знать: `ast/semantic/**` — самая крупная подсистема (около 3550 строк,
почти всё это вывод типов), а `ir/hir/**` содержит и определение HIR, и весь
`ast_to_hir`. Ни один файл больше не превышает 800 строк.

## Сборка и линты

```bash
cargo build -p jmcc
cargo clippy -p jmcc
cargo fmt -p jmcc
```

Своих тестов у `jmcc` нет: `cargo test` покрывает только `jmcdata`. Проверка
изменения — компиляция фикстуры и чтение дампа:

```bash
RUST_LOG=warn cargo run -p jmcc -- compile jmcc/tests/case2.jc --emit hir,mir,json -O0
```

Линты воркспейса агрессивны: включены сотни проверок, включая
`clippy::print_stdout`, `clippy::cognitive_complexity` и `clippy::too_many_lines`.
`#[allow]` и `#[expect]` без указанной причины не добавляются, а `#[expect]`
предпочтителен: он сам сообщит, когда перестал быть нужен.
