# jmcdata

> [!NOTE]
> Английская версия доступна в [README.md](README.md).

Модель схемы `JustMC`: что такое действие, событие, игровая величина и их
аргументы — и как это выглядит в JSON.

Крейт нужен двоим. Компилятор `jmcc` берёт отсюда имена и наборы аргументов,
чтобы проверить программу на `.jc` и собрать модуль. Мок `jmcmock` читает этим
же типом тот JSON, который компилятор выдал, — иначе мок пришлось бы учить
схеме заново, и две модели неизбежно разъехались бы.

Раньше этой роли у крейта не было видно: он был списком констант для генератора
кода. Сейчас это единственное место, где записано, что такое модуль `JustMC`.

## Из чего состоит

| Файл | Что это |
|---|---|
| `assets/actions.json` | 956 действий: 332 `variable`, 227 `entity`, 205 `player`, 128 `world`, 35 `select`, 12 `repeat`, 11 `code`, 6 `controller` |
| `assets/events.json` | 186 событий |
| `assets/game_values.json` | 196 игровых величин |
| `assets/selectors.json` | выделения: 8 для игрока, 11 для сущности, 9 для игровой величины |
| `assets/tests/test1.json` | образец модуля, на котором стоит тест |
| `build.rs` | генератор: `main` читает JSON и по порядку зовёт генераторы, пишет `generated.rs` |
| `build/` | модули генератора: `assets` (чтение схемы), `enums` (перечисления и `as_str`), `actions` (`ActionDef` и `ACTION_DEFS`), `op_builder` (методы `Op`), `lookups` (`phf`-карты), `library` (сборка `TokenStream`), `util` |
| `src/generated.rs` | `include!(concat!(env!("OUT_DIR"), "/generated.rs"))` — сгенерированный код |
| `src/module.rs` | модель модуля: то, что компилятор пишет и мок читает |
| `src/op_builder.rs` | сборка операции вручную, без сгенерированных методов |
| `src/consts.rs` | пределы `JustMC`: обработчиков на этаж и этажей |
| `src/tests.rs` | тесты |

Действие в схеме — это не только имя. У него есть `object` (группа), `type`
(`basic`, `container`, `basic_with_conditional`, `container_with_conditional`),
список `args`, необязательные `assign` (куда писать результат), `origin`
(имя аргумента, в который попадает получатель вызова метода), `boolean`
(годится ли как условие) и `lambda` (тело, которое действие выполнит само).

Про `origin` стоит сказать отдельно, потому что имя обманчиво. Это не «что
действие порождает», а «куда положить того, от кого вызван метод». У
`variable::greater` в схеме лежит `origin: "value"`, и `a.greater(b)` компилируется
в `if_variable_greater(value=a, compare=b)`: получатель `a` уходит в `value`
именно потому, что так записано в `origin`. Компилятор помечает этот аргумент
занятым ([`hir.rs`](../jmcc/src/ir/hir.rs), `initial_used_params`), чтобы
позиционные аргументы не сели на то же место.

## Сгенерированный код

`build.rs` запускается до сборки крейта, читает `assets/*.json` и пишет
`OUT_DIR/generated.rs`. Поправить схему `JustMC` — значит поправить
`assets/*.json` и пересобрать; **`generated.rs` руками не редактируется**, он
целиком перезаписывается при каждой сборке и живёт вне репозитория, в каталоге
сборки.

Что получается на выходе:

* перечисления `ActionId`, `EventId`, `GameValueId`, `ValueType`, `ArgType` —
  по варианту на строку схемы;
* по одному перечислению на каждый встречающийся набор значений аргумента
  (`WaitTimeUnit`, `StartProcessTargetMode`, …) с методом `as_str()`,
  возвращающим строку схемы;
* `ActionArg` и `ActionDef` — описание действия и его аргумента;
* `impl Op<'_>` с методом-конструктором на каждое действие;
* `phf`-таблицы с `get_action_id`, `get_action_def`, `get_action_def_by_id`,
  `get_game_value_type` и статические `SELECTOR_*_MAP`.

### Имя метода — это `object` и `name`, а не идентификатор

Конструктор операции называется `<object>_<name>`, где оба поля взяты из схемы.
Идентификатор действия и имя метода совпадают не всегда:

```rust
// ActionId::ControllerException, а метод:
Op::controller_catch_exception(variable, exception_type, operations)
```

Поэтому искать метод по имени варианта перечисления — неверно.

### Почему у перечислений есть `as_str()`

Строка схемы пишется в `#[serde(rename = ...)]` дословно, а имя варианта
приходится выводить через `heck`. `heck` не обратен `serde`: `XZ` и `XYZ`
дают один и тот же идентификатор, и `Self` идентификатором быть не может.
Поэтому имена вариантов разрешаются счётчиком (`Xz`, `Xyz`, `Itself`), а
`as_str()` возвращает то, что записано в схеме. Без него сериализация варианта
дала бы неверную строку. Тест `enum_identifiers_roundtrip_through_serde`
проверяет ровно это:

```rust
assert_eq!(Mode::Xyz.as_str(), "XYZ");
assert_eq!(Mode::Xz.as_str(), "XZ");
```

Тот же `as_str()` есть и у перечислений действий, событий и типов значений: им
ключуется `ACTION_DEF_BY_ID` (см. ниже), потому что `phf_codegen` хеширует ключи
во время сборки и не может взять тип, который порождается этим же скриптом.

### Ключи таблиц поиска

`get_action_id` и `get_action_def` принимают `object` и `name` по отдельности и
ключуются кортежем `(object, name)` — без склейки в `String` на каждый вызов:

```rust
let def = jmcdata::generated::get_action_def("variable", "greater").expect("such an action exists");
assert_eq!(def.id, "if_variable_greater");
assert_eq!(def.object, "variable");
```

Обратный индекс `get_action_def_by_id(ActionId)` возвращает то же описание по
варианту перечисления: `jmcmock` берёт из него свойства действия, а `jmcc` —
признак `boolean`. Ключ — строка id (`ActionId::as_str`), потому что `phf` не
умеет хешировать сгенерированное перечисление; сами описания лежат в одном
массиве `static ACTION_DEFS: [ActionDef; N]`, на элементы которого ссылаются
обе таблицы, то есть в бинаре хранятся в одном экземпляре.

Таблицы выделений (`SELECTOR_PLAYER_MAP`, `SELECTOR_ENTITY_MAP`,
`SELECTOR_GAME_VALUE_MAP`) лежат открыто, без функций-обёрток. Ключ — исходное
написание, значение — приведённое: `normalize_selector` снимает приставки
`player_`/`_player` и `entity_`/`_entity`, включая множественное число, и
обе формы ведут к исходной. Так `default_player` и `player_default` — одно и
то же выделение.

## Модель модуля

Модуль — это список обработчиков. Обработчик бывает трёх видов: реакция на
событие, процесс и функция.

```
Module { handlers: Vec<Line> }
        │
        └─ Line ─┬─ line_type: Event | Process | Function
                 ├─ position: u16       — номер строки в редакторе
                 ├─ operations: Vec<Op> — тело
                 └─ line_value ─── Event { event }        — что за событие
                                 └─ Fn { name, values }    — имя, параметры
```

Операция — это одно действие:

```
Op ─┬─ action: ActionId
    ├─ values: LiteMap<имя аргумента, Value>   — аргументы
    ├─ operations: Option<Vec<Op>>             — тело контейнера
    ├─ conditional: Option<Conditional>        — условие контейнера
    ├─ selection: Option<Selection>            — над чем выполняется
    └─ is_inverted: Option<bool>               — «иначе»
```

Значение — то, что может стоять в аргументе:

| Вариант | Что это | Тег в JSON |
|---|---|---|
| `Array` | список значений, элемент может быть пустым | `array` |
| `Block` | блок Minecraft | `block` |
| `Enum` | одно из фиксированного набора, может быть с переменной | `enum` |
| `Item` | предмет | `item` |
| `Location` | точка: `x`, `y`, `z`, `yaw`, `pitch` | `location` |
| `Map` | словарь | `map` |
| `Number` | число или выражение-строка | `number` |
| `Particle`, `Potion`, `Sound` | эффекты | одноимённые |
| `Text` | текст с режимом разбора | `text` |
| `Variable` | имя и область видимости | `variable` |
| `Vector` | `x`, `y`, `z` | `vector` |
| `GameValue` | игровая величина и её выделение | `gamevalue` |
| `Parameter` | объявление параметра обработчика | `parameter` |
| `Error` | значение по умолчанию | `error` |

`Number` бывает числом (`Simple`) и строкой-выражением (`Calc`). `TextParsing`
говорит, как текст разбирать: `plain`, `legacy`, `minimessage`, `json`.

Область видимости переменной (`VariableScope`) называется в схеме `game`,
`line`, `local`, `save`; вариант перечисления — `Global`. `as_str()` возвращает
`game`, потому что именно так пишет схема.

### Мелочи, на которых легко ошибиться

**Аргументы и параметры — это массив, а не объект.** Порядок аргументов схеме
важен, поэтому `values` сериализуется как `[{ "name": ..., "value": ... }, ...]`.
Словарь `Map`, наоборот, — настоящий JSON-объект, но его ключи сами являются
сериализованными `Value`. Так ключом становится текст с типом и режимом
разбора, а не голая строка.

**Число пишется без дробной части, если она нулевая.** `serialize_float`
отдаёт целое, когда `fract() == 0`, — иначе `{"number":1.0}` разошлось бы с
тем, что ждёт `JustMC`.

**Имена перечислений приводятся к `UpperCamel` при разборе.** Схема может
хранить `SOME_THING`; `deserialize_upper_camel` оставляет строку, если она уже
из заглавных букв и подчёркиваний, и переводит в `UpperCamel` иначе.

**Неизвестный обработчик пропускается, а не ломает разбор.** `deserialize_handlers`
пропускает всё, что не объект. Модуль `JustMC` может содержать больше, чем
умеет модель, и падать на постороннем элементе было бы хуже, чем его не
заметить.

**Про область видимости в `type_name()`.** Метод `Value::type_name()` для
переменной возвращает `%var(x)`, `%var_line(x)`, `%var_local(x)`,
`%var_save(x)` — **без закрывающего `%`**. Это и есть та форма, в которой
значение переменной попадает в текст программы, и её обязан понимать
тот, кто текст подставляет.

## Пределы `JustMC`

```rust
MAX_HANDLERS_PER_FLOOR = 23   // обработчиков на этаж
MAX_FLOORS            = 15    // этажей
MAX_HANDLERS          = 345   // всего
```

Это ограничение редактора `JustMC`, а не компилятора: этажи добавляются
командой `/editor floor add`. Компилятор о нём не проверяет — модуль с
большим числом обработчиков соберётся, но в редактор не влезет.

## Как поправить действие

1. Найти действие в `assets/actions.json` (или добавить новое).
2. Пересобрать: `cargo build -p jmcdata`. `build.rs` объявляет
   `cargo:rerun-if-changed=assets`, поэтому изменение JSON само запускает
   генерацию.
3. Если действие новое — проверить, что появился конструктор
   `<object>_<name>`, и дописать его обработку в моке
   ([`jmcmock`](../jmcmock/README.md)).

Так же правится и всё остальное: событие, игровая величина, выделение. Ни одна
таблица в коде не дублирует схему, поэтому расхождений между ними быть не
может — но и «поправить только компилятор» тоже не выйдет.

## Тесты

```bash
cargo test -p jmcdata
```

Их три, и все — про разбор и запись JSON:

* `deserializes_and_roundtrips_a_reference_module` — образец модуля
  deserializes и сериализуется обратно;
* `enum_identifiers_roundtrip_through_serde` — `as_str()` совпадает с тем, что
  даёт сериализация, для спорящих написаний `XYZ`/`XZ`;
* `map_serializes_as_a_json_object` — словарь пишется объектом, а не массивом.

Тест на всё остальное — это сборка компилятора и мока: если схема разъехалась,
ломается не `jmcdata`, а они. Ни один тест не проверяет, что в `assets/*.json`
лежит полная схема `JustMC`: это внешние данные, и полноту их неоткуда взять.
