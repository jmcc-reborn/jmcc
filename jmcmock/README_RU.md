# jmcmock

> [!NOTE]
> Английская версия доступна в [README.md](README.md).

Мок-рантайм `JustMC`: загружает JSON, который выдал `jmcc`, и выполняет его.

Мок нужен, чтобы прогнать программу на `.jc` без сервера: увидеть, что она
делает с миром, и получить ошибку там, где программа сломана. Своей модели
данных у мока нет — берётся [`jmcdata::module`](../jmcdata/README.md), тот же
самый, которым компилятор описывает программу. Своё здесь только исполнение:
что значит каждое действие и что происходит между действиями.

Отдельного анализатора в моке нет и не должно быть: статику — типы, имена,
наборы аргументов — проверяет компилятор. Мок ловит то, что видно только в
момент выполнения, и в этом его смысл.

## Запуск

```bash
cargo build -p jmcmock

# сначала модуль, потом прогон
RUST_LOG=warn cargo run -p jmcc -- compile jmcc/tests/nn.jc --emit json
./target/debug/jmcmock jmcc/tests/nn.json -e player_chat --chat '@train_nn'

# что есть в модуле
./target/debug/jmcmock jmcc/tests/nn.json --list
```

| Ключ | Значение |
|---|---|
| `<module.json>` | модуль, который выдал `jmcc --emit json` |
| `-e, --event <NAME>` | какое событие разыграть; ключ можно повторить, события выполняются в заданном порядке. Без ключа разыгрывается `world_start` |
| `-s, --scenario <FILE>` | запустить декларативный JSON-сценарий (симуляция игроков, событий и проверок) |
| `--chat <TEXT>` | текст события `event_chat_message` (`%event_chat_message%`) |
| `--slot <N>` | номер слота события `event_slot` |
| `-p, --player <NAME>` | добавить игрока в мок-мир; ключ можно повторить |
| `--no-default-player` | не создавать игрока `Dev`, с которого начинается мок-мир |
| `--unimplemented <error\|record\|ignore>` | что делать с действиями, семантики которых мок не знает; по умолчанию `error` |
| `--step-limit <N>` | предел числа операций за прогон (по умолчанию 5 000 000) |
| `--ticks <N>` | бюджет виртуальных тиков на событие (по умолчанию 100); синоним `--tick-limit` |
| `--save <FILE>` | файл переменных области `save`: читается при старте, записывается в конце |
| `--list` | показать события, функции и процессы модуля и выйти |

Журнал мира идёт в стандартный вывод, пояснения и ошибки — в стандартный вывод
ошибок. Код возврата — `SUCCESS`, если всё прошло, и `FAILURE`, если прогон
упал: ошибка времени выполнения, неизвестное событие, нечитаемый файл.

Журнал печатается и при ошибке. Это не удобство, а требование: журнал
показывает, что программа успела сделать до того, как сломалась, а молчаливое
«выполнено» без единой записи выглядит как исправная программа, которая ничего
не делает, — хотя на самом деле не выполнилось ни одной строки.

Событие выполняет все объявленные под ним обработчики в порядке их следования
в модуле: компилятор заводит отдельный обработчик на каждый блок `event<...>`,
а проект, разложенный по файлам, объявляет одно событие несколько раз —
например, `player_right_click` в `land.jc`, `attack.jc` и `build.jc`. У каждого
обработчика свой поток и свои локальные переменные; ошибка в одном
останавливает прогон, а журнал показывает, докуда дошёл сломавшийся.

## Что умеет мок

Действий в схеме `JustMC` почти тысяча, и большая часть из них — про предметы,
блоки, NBT и сообщения конкретной версии Minecraft. Мок реализует всё, что
влияет на вычисления и управление; остальное объявляется нереализованным.

| Объект схемы | Мок умеет | В схеме | Что это |
|---|---:|---:|---|
| `variable` | 49 | 332 | вычисления, списки, словари, тексты, ветвления над значениями |
| `code` | 10 | 11 | ожидание, возврат, вызовы, `measure_time`, исключения |
| `controller` | 3 | 6 | `measure_time`, `exception`, `do_not_run` |
| `repeat` | 7 | 12 | повторы, включая `repeat_while` и `repeat_forever` |
| `select` | 32 | 35 | выделение целей |
| `player` | 8 | 205 | сообщения, звук, полоса босса, урон события |
| `world` | 2 | 128 | урон события, отмена события |
| `entity` | 0 | 227 | действия, для которых нужен настоящий Minecraft |
| **итого** | **111** | **956** | |

Что именно не реализовано и почему — не ошибка и не недоделка, а осознанная
граница. У мока нет блоков, инвентарей, физики и NBT, поэтому
`set_variable_get_item_name` или `entity_teleport` он выполнить не может.
Пропустить их молча нельзя: программа выглядела бы исправной, а её поведение
отличалось бы от серверного. Поэтому по умолчанию такое действие останавливает
прогон ошибкой `Unimplemented`, а `--unimplemented record` и `ignore` заменяют
ошибку на запись в журнал или на тишину — для случая, когда надо прогнать
чужой модуль и посмотреть, докуда он дойдёт.

## Мир и журнал

Мир мока — это игроки и сущности, у каждой есть имя, UUID и позиция. Мир по
умолчанию состоит из одного игрока `Dev`: событиям должно быть на ком
выполняться, иначе большинству действий `player_*` просто нечего делать.

Эффекты действий не меняют мир, а записываются в журнал — по строке на каждую
цель кадра. Формат строки:

```
[тик] <player|entity> <имя>: <действие> <подробность>
```

Если целей у кадра нет, строка всё равно пишется и помечается `<no target>` —
иначе действие, выполнившееся вхолостую, исчезло бы из виду.

```
[0] player Dev: player_send_message Начало обучения...
[0] player Dev: player_send_message [[], 0.01]
```

Журнал ограничен 100 000 записями; о переполнении мок сообщает в стандартный
вывод ошибок, а не молчит.

## Декларативные сценарии

Мок поддерживает запуск многопользовательских сценариев и сложных цепочек действий из JSON-файла (`-s, --scenario <FILE>`). Это позволяет моделировать действия нескольких игроков, события с кастомными аргументами, продвижение игрового времени и валидацию журнала.

```bash
./target/debug/jmcmock module.json -s scenario.json
```

### Формат файла сценария

Файл может быть объектом с метаданными либо плоским массивом шагов `[ { "type": "..." }, ... ]`:

```json
{
  "name": "Тест многопользовательского взаимодействия",
  "description": "Игрок Alice пишет в чат, заходит Bob и кликает в инвентаре",
  "initial_players": ["Alice"],
  "no_default_player": true,
  "steps": [
    { "type": "event", "event": "world_start" },
    { "type": "event", "event": "player_join", "player": "Alice" },
    { "type": "event", "event": "player_chat", "player": "Alice", "chat": "!start" },
    { "type": "assert_log", "contains": "Игра началась" },
    { "type": "add_player", "name": "Bob", "x": 10.0, "y": 64.0, "z": 20.0 },
    { "type": "event", "event": "player_join", "player": "Bob" },
    { "type": "wait", "ticks": 20 },
    { "type": "assert_log", "contains": "Bob присоединился", "not_contains": "Ошибка" }
  ]
}
```

### Доступные типы шагов

| Тип шага (`type`) | Поля | Описание |
|---|---|---|
| `add_player` | `name`, `x`, `y`, `z` (опционально) | Добавляет нового игрока с координатами в мир |
| `remove_player` | `name` | Удаляет игрока из мира |
| `event` | `event`, `player`, `chat`, `slot`, `title` | Вызывает событие от лица игрока или мира |
| `call_function` | `name` | Прямой вызов функции модуля |
| `wait` | `ticks` (по умолчанию 1) | Продвигает виртуальное время мира на заданное количество тиков |
| `assert_log` | `contains`, `not_contains`, `exact` | Проверяет записи журнала; при несовпадении выбрасывает `AssertionFailed` |
| `clear_log` | — | Очищает журнал мира для изоляции последующих проверок |

## Переменные

Четыре области видимости `JustMC` различаются не столько видимостью, сколько
временем жизни:

| Область | Живёт | Где хранится |
|---|---|---|
| `line` | один кадр вызова; кадр завершился — переменные исчезли | у каждого кадра своё хранилище |
| `local` | один процесс или событие вместе со всеми вложенными вызовами | одно на процесс |
| `game` | всё время работы кода | рантайм |
| `save` | как `game`, но переживает перезапуск | рантайм, плюс файл |

Различимы три состояния переменной, и означают они разное:

* **нет в хранилище** — переменной не существует, чтение это ошибка
  `UndefinedVariable`;
* **есть, значение пустое** — переменная объявлена, но не записана; `JustMC`
  подставляет вместо неё `0` или пустой текст, и мок делает то же самое;
* **есть, значение записано** — обычное чтение.

Строчные переменные объявляются в начале кадра, а не в момент первого
присваивания. Компилятор свободно читает переменную, которую записали только в
одной из ветвей (так устроены временные `__ct`), и это работает именно потому,
что к началу строки переменная уже есть — пустая. Мок повторяет это: при
загрузке модуля он проходит по телу каждого обработчика и объявляет все имена,
которые где-нибудь в нём встречаются со `scope: line`.

Возврат значения из функции держится на общей `local`: компилятор пишет `ret`
как локальную переменную, вызываемый её заполняет, вызывающий читает сразу
после вызова. Поэтому хранилище `local` одно и то же для всего процесса или
события.

Переменные `save` сохраняются только тогда, когда владелец рантайма позовёт
`Runtime::persist_save` — командная строка делает это по `--save <FILE>`.
Сам мок `Ctrl-C` не перехватывает и о том, что «программа завершается», не
знает: это решение того, кто рантаймом пользуется.

## Что проверяется во время выполнения

Компилятор ловит всё, что видно статически. Мок ловит остальное и никогда не
пропускает это молча:

| Ошибка | Когда |
|---|---|
| `UndefinedVariable` | переменной нет в её области видимости в момент чтения |
| `UnsetVariable` | переменная объявлена, но не записана, а её читают как значение |
| `UnknownFunction`, `UnknownProcess`, `UnknownEvent` | обработчика нет в модуле |
| `MissingParameter`, `UnknownParameter` | набор аргументов не совпал с объявленными параметрами |
| `UnknownArgument`, `MissingArgument` | аргумента нет в схеме действия либо обязательного аргумента не хватило |
| `Unimplemented` | семантику действия мок не знает |
| `UnimplementedSelection` | выделение называет участника события (`victim_*`, `damager_*`, `projectile`), которого мок не разыгрывает |
| `ExpectedVariable`, `UnexpectedValue` | на месте переменной не переменная; значение нечем записать |
| `NotANumber`, `NotText`, `NotAList`, `NotAMap`, `NotALocation`, `NotAVector` | значение не того вида, которого требует действие |
| `DivisionByZero`, `IndexOutOfRange` | арифметика и списки |
| `NoTarget` | действие требует цели, а её нет ни у кадра, ни у мира |
| `MisplacedElse` | `else` без `if` |
| `StepLimitExceeded` | прогон упёрся в предел шагов |
| `Raised` | `control_call_exception` поднял исключение |

Часть ошибок ловится `controller_exception`, часть — нет: исключение, которое
означает несогласованность самого модуля (`Unimplemented`,
`StepLimitExceeded`, `UnknownFunction`, `MisplacedElse`), перехватить нельзя —
так же, как на сервере нельзя перехватить глобальную ошибку.

## Текст и приведение типов

### Плейсхолдеры

`%player%`, `%var(x)%` и прочие подставляются в тот момент, когда значение
используется, а не когда записывается: `set var = "%player%"` кладёт в
переменную уже подставленный ник.

Имена переменных проходят через подстановщик тоже. `game var %player%_dialog` —
это по переменной на игрока, а не буквальный `%` в имени; без подстановки
`player_join` писал бы в одну переменную, а `start_process` читал бы из другой.

Значение переменной в тексте компилятор записывает как `%var(x)` — **без
закрывающего `%`** (так разворачивается `"${x}"` внутри литерала:
`"${owner}_victim"` становится `%var(owner)_victim`). Поэтому кроме основной
формы `%имя%` мок понимает и форму вызова `%имя(аргумент)` до закрывающей
скобки. Без этого подстановка просто не состоялась бы, а в журнал попало бы
`%var(owner)_victim` — текст, которого в программе не было, и без единой
ошибки.

Отличия, которые важно знать:

* `%var(x)%` — это чтение переменной, и отсутствие переменной здесь такая же
  ошибка `UndefinedVariable`, как и чтение её в аргументе действия;
* `%что-то-неизвестное%` мок не знает и оставляет в тексте как есть: это может
  быть игровая величина, которой у мока нет;
* `%math()` не вычисляется: вычислитель выражений в мок не входит, а тихо
  вернуть исходный текст значило бы скрыть ошибку. Встреченный `%math()`
  объявляется нереализованным.

Цветовые коды `legacy` (`&a`, `&l`, `&#RRGGBB`) снимаются — иначе подсчёт
длины текста и сравнение давали бы результат, которого никто не ожидает.

### `as` — это фича `JustMC`, а не преобразование

`as` в `JustMC` **значения не преобразует**. Он помечает тип для компилятора, а
приводит значение само действие: в действиях аргумент объявлен текстовым, и
всё, что в него попало, читается как текст. Поэтому экземпляр класса — а
компилятор описывает его списком полей, — попавший в текстовый аргумент через
`as text`, не ошибка:

```
[0] player Dev: player_send_message [[], 0.01]
```

Пользовательского кода это **не касается**: параметры функций и процессов,
сравнение значений и запись в переменную тип не меняют, и значение там остаётся
собой. Приведение есть только в аргументах действий.

Ровно так устроен и мок: приведение живёт там, где читается аргумент действия,
а `value::as_text` остаётся частичным — его используют сравнение, перечисления
и разбор значений, и там приведение «до текста» было бы неверным.

### Единственное место, где текст зависит от мока

Серверного представления списка, словаря, локации и вектора у мока нет, и
повторить его он не может. Составные значения записываются формой, которую мок
придумывает сам:

| Значение | Как выглядит в тексте |
|---|---|
| список | `[a, b]` |
| словарь | `{ключ: значение, ...}` |
| локация | `(x, y, z, yaw, pitch)` |
| вектор | `(x, y, z)` |

Это единственное место в моке, где текст зависит от него, а не от программы.

## Чем мок отличается от сервера

Это список известных расхождений. Они не ошибки мока, а следствия того, что
сервера у него нет.

**Время.** `control_wait` не спит, а двигает часы мира: тики прибавляются
сразу, один тик равен 50 мс (20 тиков в секунду). Программа с ожиданиями
выполняется мгновенно. `controller_measure_time` замеряет разницу часов мира,
а не секундомера: код без ожиданий в моке занимает ноль времени. Это ровно то,
что обещает справка `JustMC` — «учитывает блоки Ждать», — но в моке это
означает буквально тики.

**Процессы выполняются синхронно.** `start_process` в `JustMC` заводит
отдельный поток, который живёт своей жизнью. В моке потока нет, поэтому процесс
выполняется тут же, до конца, и `start_process` — это вызов, а не запуск.
Порядок эффектов в журнале от этого отличается от серверного. Так же ведёт
себя `controller_async_run`.

**Метки.** `controller_label` и `control_break_label` требуют стека меток в
кадре, которого у мока нет. `controller_isolated_selection` требует модели
изолированной выборки. Все три объявлены нереализованными: `break` по метке,
сработавший не там, увёл бы программу по неверной ветви молча.

**Выделения.** Понимаются `default`, `current`, `default_player`,
`default_entity`, `all`, `all_players`, `all_entities`, `last_entity`.
Участники события — `victim_*`, `damager_*`, `shooter_*`, `killer_*`,
`projectile` — недоступны: мок не разыгрывает само событие, а подставить
вместо них цель кадра значило бы выдать её за участника.

**Игровые величины.** Читаются `event_chat_message`, `event_item`,
`event_slot`, `open_inventory_title`, `selection_size`, `cpu_usage`,
`location`, `current_health` (только у игрока). Выделение величины понимается
только `default` и `current`: мок читает величины у одной цели, и других
выделений у него нет. `%cpu_usage%` показывает число выполненных шагов, а не
время — сервера и процессора у мока нет.

**Промах `select_*` — не ошибка.** `select_player_by_name("Вася")` на сервере,
где Вася не заходил, даёт пустое выделение, и следующее действие не делает
ничего. Это обычный ход программы, и мок повторяет поведение сервера, а не
жалуется. Нереализованным объявляется только то, чего мок не умеет.

**Сущности.** Мок-мир не делит сущности на мобов и не-мобов: всё, что попало в
мир, считается мобом. Поэтому `select_all_mobs` и `select_all_entities` дают
одно и то же, а «последняя сущность» — это последняя добавленная: мок сущности
не удаляет.

**Списки.** Нумерация с нуля. `get_list_value` вне границ даёт `default_value`,
а если его нет — пустое значение: у этого действия значение по умолчанию прямо
объявлено аргументом. Запись по индексу вне границ, наоборот, останавливает
выполнение `IndexOutOfRange`: значения по умолчанию у неё нет. `get_char_at`
вне границ даёт пустой текст.

**Ловушка исключений.** `controller_exception` с типом `WARNING` берёт только
предупреждения, `ERROR` — всё остальное перехватываемое. Глобальные и
критические ошибки не улавливаются — как и написано в справке `JustMC`.

| Модуль | Что делает |
|---|---|
| `lib.rs` | точка входа крейта: документирует времена жизни переменных и что проверяется только во время выполнения, а также переэкспортирует `Program`, `Runtime`, `World`, `Config` и ошибки |
| `main.rs` | командная строка: разбор ключей, печать журнала и итога |
| `run/` | загрузка модуля, индексы обработчиков, кадры, запуск событий, `save`: `mod` (типы `Program`/`Runtime`/`Stream` и индексация), `events`, `calls`, `steps`, `vars` |
| `interp/` | вычисление значений, ветвления, доступ к переменным, аргументы действий: `mod` (`Flow`/`Args`), `exec` (исполнение и ветвления), `eval` (значения), `args` (аргументы `Op`), `select` (выборки) |
| `value.rs` | значения времени выполнения, сравнение, приведение к числу и тексту |
| `world.rs` | игроки, сущности, выделения, журнал |
| `scope.rs` | области видимости переменных и их времена жизни |
| `text.rs` | подстановка плейсхолдеров, снятие цветовых кодов |
| `schema.rs` | доступ к схеме `jmcdata`; обратный индекс `ActionId -> ActionDef` берётся из `get_action_def_by_id` |
| `error.rs` | `RuntimeError` и его перехватываемость |
| `config.rs` | `Config`: предел шагов, режим для нереализованного, файл `save` |
| `actions/` | действия по группам схемы: `variable` (`mod` + `arithmetic`/`lists`/`maps`/`text`/`state`), `code`, `repeat`, `select`, `effect` |

Группа действия — это `object` из схемы `JustMC`, тот же самый, которым схема
сама разложила действия. Своей таблицы «действие — группа» мок не заводит: она
разъехалась бы со схемой. Новое действие схемы попадает в свою группу само, а
если группа его не знает — оно объявляется нереализованным, а не пропускается
молча.

## Гейты

```bash
cargo fmt -p jmcmock
cargo check -p jmcmock --all-targets
cargo clippy -p jmcmock --all-targets -- -D warnings
```

`jmcmock` держится без предупреждений: у него нет ни одного `#[allow]` без
причины, а [`missing_docs`](src/lib.rs) объявлен на уровне крейта, так что
публичный элемент без документации — это предупреждение, а не молчание.
Единственное место, где можно печатать в стандартный вывод, — `main.rs`, и это
помечено явно: печатать журнал и есть работа этой программы.

Компилятор и мок собираются вместе, поэтому из корня репозитория работает
`cargo build` и `cargo clippy` по всему воркспейсу.

## Пример

```rust
use jmcmock::{Program, Runtime};

let text = std::fs::read_to_string("jmcc/tests/nn.json")?;
let program = Program::parse(&text)?;
let mut runtime = Runtime::new(&program)?;
runtime.fire_event("world_start")?;
for entry in runtime.world().log().entries() {
    println!("{entry}");
}
# Ok::<(), Box<dyn std::error::Error>>(())
```
